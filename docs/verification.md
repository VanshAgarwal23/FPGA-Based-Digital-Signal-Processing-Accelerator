# Verification Report

## 1. Introduction

The DSP Accelerator was verified through RTL simulation using a dedicated Verilog testbench.

The verification process was designed to check the functional correctness of the FIR processing operation, fixed-point arithmetic, signed data handling, reset behavior, valid-signal control, and output saturation.

The final verification environment uses a reference model to calculate the expected output and compares it with the output generated by the Device Under Test (DUT).

---

## 2. Verification Objectives

The main objectives of verification were:

* Verify correct FIR filtering operation.
* Verify signed 16-bit input and output handling.
* Verify Q1.15 fixed-point scaling.
* Verify output saturation.
* Verify correct sample-history behavior.
* Verify `input_valid` handling.
* Verify `output_valid` behavior.
* Verify reset functionality.
* Verify operation across different input patterns.
* Verify operation under large positive and negative values.
* Detect arithmetic and state-related errors.

---

## 3. Testbench Architecture

The testbench consists of:

1. Clock generation
2. Reset generation
3. Input stimulus generation

## 4. Reference Model

The reference model implements the expected FIR calculation:

```text
y[n] = Σ x[n-k]h[k]
```

The model maintains the input sample history and performs the same fixed-point scaling and saturation operations expected from the RTL design.

After accumulation, the result is scaled using:

```text
scaled_result = accumulated_result >>> 15
```

The result is then saturated to the signed 16-bit range:

```text
-32768 to +32767
```

This allows every DUT result to be compared against an independently calculated expected result.

## 6. Test Categories

The verification suite contains multiple categories of functional tests.

### 6.1 Normal Operation Tests

These tests verify normal FIR processing using representative input values.

The expected output from the reference model is compared with the DUT output.

### 6.2 Signed Data Tests

Positive and negative input samples are applied to verify signed arithmetic.

These tests check that:

* Positive values are processed correctly.
* Negative values are processed correctly.
* Positive and negative values can occur in the same sequence.
* Signed multiplication and accumulation produce the expected result.

### 6.3 Input Valid Gap Tests

The testbench introduces gaps in the `input_valid` signal.

These tests verify that invalid input cycles are not incorrectly interpreted as new valid samples.

### 6.4 Random Input Tests

Randomized input values are applied to exercise a broad range of operating conditions.

Random testing helps detect arithmetic and state-related errors that may not appear in deterministic test patterns.

### 6.5 Long Random Stream Tests

A longer sequence of random samples is used to verify continuous operation of the FIR processing path.

This also exercises the sample-history mechanism over many consecutive transactions.

### 6.6 Saturation Tests

Large positive and negative input conditions are applied to exercise the output saturation logic.

The expected result is checked against the signed 16-bit limits:

```text
Maximum =  32767
Minimum = -32768
```

### 6.7 Zero After Large Values

Tests are included in which large input values are followed by zero values.

These tests verify that previous samples are correctly handled by the FIR history and that the output does not incorrectly remain at a previous saturated value.

### 6.8 Sign Transition Tests

Input sequences containing transitions between positive and negative values are used to verify correct signed arithmetic and filter-history operation.

---

## 7. Test Execution

The testbench reports the result of each individual comparison.

For each test, the expected output generated by the reference model is compared with the actual DUT output.

A test is counted as passed when the expected and actual results match.

A test is counted as failed when a mismatch occurs.
